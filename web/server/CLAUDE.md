# web/server: the tester app server (Lane A, Abhinav)

Wraps the orchestrator behind a small HTTP API for invited testers. Plan: `plan/web-plan.md` (T40 to T50). The API is frozen in `contracts/web/` (tag `contracts-web-v1.0.0`): never edit it from here; follow `contracts/web/README.md` for the check order, the status per code and the fixed messages.

## Run and test
- `node web/server/server.mjs [--port 8787] [--data-dir web-data] [--orchestrator orchestrator/cli.mjs] [--timeout-min 45] [--daily-usd-cap 0] [--allow-local] [--viewer-port 8788] [--viewer-script web/viewer/server.mjs] [--no-viewer]`. It starts the results viewer as a child process when its script exists (output in `<data dir>/viewer.log`), and says "results cannot be viewed" when it does not. `--no-viewer` starts none (the manifest links still point at `--viewer-port`).
- `node web/server/admin.mjs [--data-dir web-data] invite add <label> | invite list | invite reset <label> | invite revoke <label> | live <job_id> on|off | spend`. `invite add` prints the code once. Use the same `--data-dir` as the server.
- `cd web/server && node --test` (no network, no real crawl, never a paid model). The tests validate every body with the ajv in `contracts/node_modules`: run `npm ci` in `contracts/` once (the CI job `web-server` does, and a test fails in CI when ajv is missing).
- `test/fake-orchestrator.mjs` stands in for `orchestrator/cli.mjs`; each job is steered by the query string of its url (`?sleep=300&exit=1&child=1&noise=1&vcost=0.3&hcost=0.2&files=1&gate=1&costlog=story:1.2,art:2.7&upto=3&steps=1&stub=1&nolog=1&failstage=art`, see the file header). Like the real orchestrator it writes `orchestrator.log` last. `node --test` runs every file under `test/`, so the fake and `harness.mjs` do nothing when loaded without arguments. `harness.mjs` holds what the test files share (the server on an ephemeral port, the contract checks).

## Files
- `server.mjs`: routes (the event stream included), the request checks in contract order, static files of the React build `web/ui/dist/`, `startViewer`, command line.
- `queue.mjs`: job records (`web-data/jobs/<id>/job.json`), the one-at-a-time line, the child process, timeout kill, restart recovery, the live switch, the dollar cap at the head of the line, the cost of each run into `spend.json`, the stage bookkeeping (poll and final scan) and the end of a run.
- `progress.mjs`: the stage table, what the run folder says (`stagesDone`, `wasStubbed`, `failedStage`), `classifyExit`, and `createEventHub` (the events of every job, and `GET /api/jobs/:id/events`).
- `invites.mjs`: the invite store (`web-data/invites.json`), codes, hashes, the one run per Los Angeles day rule.
- `ledger.mjs`: the Los Angeles day, atomic JSON files, `spend.json`, the job id check and the name of the live flag, shared by the server and `admin.mjs`.
- `admin.mjs`: the admin tool. It edits files under the data dir and never talks to the network.
- `urlcheck.mjs`: rule 2 (`parseTarget`) and rule 8 (`checkHost`, `isPublicAddress`).
- `messages.mjs`: the fixed texts and HTTP statuses; a test compares them with the contract fixtures.

## Rules for this folder
- Node stdlib only, Node 22 and 24. No `package.json` dependencies. (`web/ui/` is React with its own dependencies; this server only reads its built files.)
- Listen on 127.0.0.1 only; there is deliberately no host option.
- The orchestrator is started with an argument array and `shell: false`. Its stdout and stderr go to `console.log` in the job folder and never to a response. Run failure text comes only from `messages.mjs`, never from scraped text or orchestrator output.
- No cookies. Static files come from `web/ui/dist/` and are read as files, never executed; `dev/` and `test/` folders, dot files and non-web file types are never served.
- A request that fails a rule never uses up an invite code, and no DNS lookup happens before rules 1 to 6 pass. The code is used up only after the job was accepted (`queue.add` first, then `recordUse`).
- Invite codes are never stored: only a salted SHA-256 hash (`invites.json`, gitignored `web-data/`), compared with `crypto.timingSafeEqual` against every entry. A job keeps the invite label, never the code. `invite_code` must be a non empty string before the store sees it.
- `--live` is added in exactly one place, `JobQueue#start`, and only for a job whose `live.flag` exists at that moment and that passed the cap check. The default cap is 0, so every live job fails at start with `budget` until Abhinav sets `--daily-usd-cap`. A free run is never refused for the cap. `daily_cap_reached` is reserved by the contract and never sent.
- No em dashes or en dashes anywhere.

## Seams for later tasks
- `queue.on('event', (job_id, name, data))` carries the shapes of `event.v1`, `stage` events included (T43); `progress.mjs` `createEventHub` subscribes and serves them.
- `createApp({ invites: { check(code) -> null | { label, usedToday }, recordUse(label) } })`: with none, every POST is refused as `invite_invalid` (the safe default). `server.mjs` wires the real store from `invites.mjs`; tests inject small stand-ins.

## Decisions made in T40 where the contract is silent
- The line holds at most 5 places (`maxLine`), the run in progress counting as one, so the 6th start request gets `queue_full`.
- A host that does not resolve (or whose lookup takes over 5 s) is refused as `bad_url`, never let through; any private address among the answers is `host_not_public`. Scout resolves the name again, so a hostile DNS that answers differently the second time is not stopped by this check: T49 step 2 probes redirects, and real isolation needs egress filtering.
- `url.href` (the normalised address that was checked) is what the orchestrator gets.
- Owner name: tabs and line breaks become a space, other control characters and Unicode format characters (category Cf: bidi controls, zero width characters, the byte order mark) are dropped, spaces collapse; a name empty after that is `owner_name_required`; the consent note holds the first 100 code points. Dropping Cf also drops the zero width joiner, so a joined emoji such as a family loses its joins.
- Static files are served at the root and under `/ui/` (both work).

## Decisions made in T47 where the plan and the contract are silent
- The store file: `{ salt, invites: [{ label, hash, created_at, revoked, last_used_day }] }`. `hash` is SHA-256 of the 16 byte salt followed by the code. Codes are 12 characters of `ABCDEFGHJKMNPQRSTUVWXYZ23456789` (about 59 bits); a typed code is trimmed and upper cased before it is hashed. Labels are 1 to 40 of letters, digits, `.`, `-`, `_`, starting with a letter or digit, unique without regard to case.
- The server and `admin.mjs` are separate processes, so every store call re-reads `invites.json` and every change writes the whole file at once (temp file, then rename). A corrupt file refuses every code, is logged, and is never overwritten. Two processes saving in the same instant could still lose one write; the admin tool is run by hand.
- If saving the use fails after the job was accepted, the job still goes ahead (it is already in the line) and the failure is logged; a disk error in `queue.add` itself fails the request with 500 and leaves the code unused.
- The cap check, when a live job leaves the line: refuse when today's spend is at or above the cap, or when today's spend plus lane budgets `b` plus `c` of the run template is over the cap (exactly reaching it is allowed). The template is `contracts/fixtures/sample/00-run.json`, the file the orchestrator starts from by default (`--fixture sample`); lane `a` has no paid model and is not counted. If `spend.json` or the template cannot be read the answer is no.
- `spend.json` is `{ "<America/Los_Angeles day>": <dollars> }`, kept by day of finishing. After every run (also failed, timed out, or killed with the server and recovered at the next start) the spend of every run folder of the job is added, rounded to a millionth of a dollar: lane B's is the sum of `cost_usd` over every line of `b-design/cost.jsonl` (Lane B appends one line per stage, story, art, council and imagery, as it ends, also when it fails), and lane C's is `cost_usd` of `50-handoff.json`. `40-verdict.json` carries the council's cost only (already in `cost.jsonl`), so it is used for lane B only when `cost.jsonl` does not exist (plan/rulings.md, 2026-11-11 T47 spend counting); an empty `cost.jsonl` means lane B spent nothing. A line of `cost.jsonl` that is not JSON, a `cost_usd` that is missing, text or negative, or a `cost.jsonl` that cannot be read fails closed: the run counts its whole lane B budget `b` (or what its good lines add up to, if that is more) and a warning is logged. A bad `cost_usd` in `50-handoff.json` or in the fallback verdict is ignored with a warning. A free run that reports a cost is warned about and still counted.
- Known gaps: a live run that dies before it writes `cost.jsonl` or `50-handoff.json` leaves that spend uncounted (the lanes enforce their own `b` and `c` caps); `admin.mjs live` on and off only work for a job that is still queued, because the flag is read once, as the job starts (a started job keeps its mode; its flag file stays as the record).

## Decisions made in T43 where the plan and the contract are silent
- Progress is read from which contract files exist in the run folder (the one child folder of the job folder): scout is running when the job starts; `10-inventory.json` ends scout, `20-storyboard.json` story, `30-directions.json` art, `40-verdict.json` council, `45-selection.json` select, `50-handoff.json` build, and the next stage begins at once. A file counts when it is a non empty plain file and every earlier stage's file is there. The files are never opened. The poll is `pollMs` (1 s; `fs.watch` is unreliable on Windows) and a file counts as a finished stage only after two polls in a row have seen it, so a lane that writes its file and then exits 3 is not reported as done first. A last scan runs when the process exits, so a stage that ended between polls is never lost and the events stay in order.
- Lanes B and C write their output file and then exit 3 when a quality gate fails (and Lane C writes a `budget` handoff and exits 4), so for a run that exits non zero the stage that failed is the one the orchestrator names in the last line of `orchestrator.log` (`FAILED stage <name> failed with exit <n> (...)`; only a name from the stage table and only the real exit code are accepted, no other text of the log is read). With no such line it is the first stage without a file, or `build` when every file is there. That stage gets a `stage` event with state `failed` just before `failed`; a stage that left its file is not announced as done first (it takes two polls in a row to see a file, so a lane that exits within about one poll never is). This is how `events-failed.sse` (build running, build failed, failed quality_gate) is produced by a real Lane C failure. If a lane lingers longer than that after writing its file (Lane B exits when its loop drains), the poller has already sent that stage `done` and the next one `running`; when the log then names the stage, `job.stages` shows it `failed` and every later stage `pending`, and the stream ends with `stage {that stage, failed}` then `failed`. event.v1 has no `pending` state and an event cannot be taken back, so a client folding the stream sees, for example, `art done`, `council running`, `art failed`, `failed`: the failed stage wins, and the stage left running is never finished. A stream is not rewritten after the fact.
- Exit mapping (`classifyExit`): a run we killed is `timeout`; exit 0 is a success only when all six files exist and the log shows no stub; exit 3 is `site_blocked` when the failed stage is scout (Scout writes no inventory when no page could be crawled) and `quality_gate` after that; exit 4 is `budget`; any other exit is `crash`. Two choices the contract leaves open, both failing closed: exit 0 with `50-handoff.json` missing is `crash` (the manifest url would answer 404), and exit 0 with an `orchestrator.log` that is missing or unreadable is `not_real` (the real orchestrator always writes one, and nothing else vouches that the result is the tester's own site).
- Stub detection: any line of `orchestrator.log` that starts with `STUB` (`STUB <stage> (lane not present)` in a real run, `STUB <stage> ok <file>` in stub mode) or contains `lane not present` makes an exit 0 run `not_real`, with six `done` stages (the contract) and then `failed`. Checked against the real orchestrator's log with the lanes missing. Only the orchestrator's own lines are in that log on a run that exited 0.
- `failed.message` and `job.error.message` are always the fixed text of `messages.mjs`. Nothing from `console.log`, `orchestrator.log` or a run file is ever sent; the tests plant markers in all three and look for them in every event and job body.
- Events are kept in memory per job, as `{ id, name, data }` with ids 1, 2, 3, ... in the order the queue emitted them, and are never written to disk. A job this process did not run itself (it finished, or was failed as `server_restarted`, before this start) has its history rebuilt from `job.json` when first asked for: `queued` with position 1 (the real place in line is not kept), `started`, one running and one done or failed event per stage that ran, then `done` or `failed`. So every stream is a valid one that ends in exactly one `done` or `failed`.
- The stream always replays the whole history from id 1 and ignores `Last-Event-ID` (contract rule), then sends live events, `: ping` every `pingMs` (15 s) and closes after `done` or `failed` (a finished job gets its history and an immediate close). A job id that is not one, or unknown, gets `404 not_found` as JSON, never a stream; other methods and other paths under `/api/jobs/:id/` are `404 not_found` too. A client that disappears is forgotten at once (`close`), and a failing write to it can never break the queue that is emitting.
- `contracts/web/fixtures/events-*.sse` were not re-recorded (the contract is frozen at `contracts-web-v1.0.0`): `sse.test.mjs` compares the parsed events of a real stream with them after replacing the job id, and the stream is equal for done, failed (both build dying before and after writing `50-handoff.json`) and queued (positions 3, 2, 1).
- The viewer (`startViewer`, only when the server runs as a program) is started with an argument array and no shell, `--jobs-root <data dir>/jobs --port <viewer port> --app-origin http://127.0.0.1:<app port>`; its output goes to `<data dir>/viewer.log`. It is not restarted: if it stops by itself that is logged once ("results cannot be viewed until the server is started again"), and a viewer left over from a killed server keeps port 8788, so the next one reports that. Stopping the server (Ctrl+C or SIGTERM) stops the viewer; a hard kill of the server (Task Manager, `taskkill /F`) does not.
- Known gap: a real run on the local sample site (`--allow-local`) streaming all six stages through `curl -N` was not done in T43: it needs Playwright for Scout, `npm ci` in `lanes/c-build` and Node 24, and T43 approves no installs. What was run instead: the server program, the fake orchestrator and `curl -N`, and the real orchestrator's own log lines with stand-in lanes (to fix the STUB and FAILED formats above).

## Decisions

- Builds run in `lanes/c-build/.work/<id>/` (gitignored), never under `runs/`, so Astro and Tailwind resolve from this lane's `node_modules`. `lib/astro-build.mjs` is the one way to build; later tasks copy the source and `dist/` into the run folder.
- Banned-library check (T06): `gsap` and `lenis` anywhere, and `three` only in module form (`three.js`, `three.module.js`, `from "three"`). A bare "three" check would fail on ordinary copy such as "three cards".
- `build.format: 'file'` so pages come out as `dist/about.html`, matching the paths in the sample handoff. `build.assetsPrefix: '.'` (T13) makes the CSS link `./_astro/...`, and nav links are `./<page>.html`; every page sits at the site root, so the site works served or opened from disk. A test fails on any root-absolute `href` or `src`.
- Pages are data, not generated code (T13): the builder writes `src/data/site.json` and one route, `src/pages/[...slug].astro`, renders every page from it. Scraped or model-written text therefore always goes through Astro's escaping, never into source code.
- Dash rule (T13, `builder/text.mjs`): a dash between numbers becomes a hyphen (`9-12`), any other em or en dash becomes `, `. Applied to every string in `site.json`. T15's verbatim check and T22's fact diff must apply the same function. Source files spell the characters as `\u2013` and `\u2014` escapes so the lane itself has none.
- Sections (T13): a hero section renders as a full-width accent band with the page's only `h1`; a page with no hero gets its title as the `h1`. Every other intent uses one generic `Section` (h2, subhead) carrying `data-intent` and `data-pattern`. The plan said one component per intent; the direction's `section_patterns` are free text ("three cards", "dated list"), so real per-pattern layouts wait for T29, when there is content to lay out. The grid width comes from `layout.grid` ("1200 px max").
- The run's site is a standalone Astro project (`c-build/site/package.json` pins the same versions as this lane; a test keeps them equal), so the owner can `npm ci && npm run build` it.
- Lane C code does not run anything in `contracts/` (lane `CLAUDE.md`); schemas and fixtures are read as JSON only. `lib/contracts.mjs` is our own Ajv 2020 check (strict, all errors) against the version each file declares.
- **Merge order (T12):** once `lanes/c-build/cli.mjs` is on main, the orchestrator runs it instead of filling the build stage from the sample. Until T23 the CLI checks inputs and budget but cannot build, so it exits 1 on valid input. Merging T12 to T22 early would turn a working stubbed build stage into a crash on Abhinav's real runs. So: T06 can merge any time; T12 to T22 stay as open PRs (reviewed, CI green) and merge together once T23 passes. A PR at that point can merge the stack in order with merge commits.
- CLI (T12): inputs are matched by their `contract` field, not their position. Unknown stage, missing `--run` or `--out`, a bad `--max-usd`, an extra contract or a duplicate are all exit 2. The budget is the smaller of `--max-usd` and `00-run.json` `limits.lane_budget_usd.c`; 0 or less exits 4 after writing a schema-valid handoff with `status: "budget"`, `gates_passed: false`, no measured QA, and a one-paragraph `c-build/report.md`. Its page paths point at files that do not exist, which is fine because the orchestrator stops on exit 4 before its cross check.
- `models.json` is `{ "build": null }`: the builder is deterministic (no model call, `cost_usd` 0). A model is added only if T29 shows the deterministic build is not good enough.
- Content (T15, `builder/content.mjs`): every body block is rendered word for word with `data-src="<block_id>"`. A list block becomes one `li` per line; a heading becomes `h3`; a quote becomes `blockquote`; anything else is a `p` with one line per text line. In an **edited** section, the block named in `edited_from_block_id` is not rendered, because the section headline is the storyteller's rewrite of it; every other block renders. A section or image id the inventory does not have is exit 2.
- Images (T15): copied from the run folder into the site's `public/images/<image_id>.<ext>` and rendered with the inventory alt text, width and height, plus `data-src`. An image with no `local_path` or no file on disk is skipped here; T23 must list it in the report as not carried over.
- Forms (T15): a form with `needs_backend` becomes a "Send us a message" note with tel and mailto links from the first phone and email facts, in the page's contact section (or its last section). No `<form>` is rendered. Forms that do not need a backend are not rendered yet; T23 must flag them.
- Build folders (T15): each build gets a fresh `mkdtemp` folder under `.work/`, because `node --test` runs test files in parallel and two builds of one run id collided.
- Accessibility gates (T21, `qa/`): the built `dist/` is served on 127.0.0.1 at a free port (`qa/serve.mjs`, refuses paths outside the folder). axe-core runs with the WCAG 2.0 and 2.1 A and AA tags on every page at desktop (1280 px) and mobile (390 px) widths; the counts are rule findings per page and width. Lighthouse runs its default mobile settings on every page and reports accessibility, performance and best practices; only accessibility is gated. Gate: zero serious, zero critical, Lighthouse accessibility at least 95 on every page. Failing exits 3 and lists each failing rule and page in plain words.
- Both tools use Playwright's Chromium (Lighthouse connects to it over a remote debugging port), so a laptop and CI test the same browser, and nothing depends on a local Chrome install. Reduced motion is forced in both, so text is never measured halfway through the fade-in.
- The full report goes to `R/c-build/axe.json` (rule id, impact, help text, link, element selectors per page and width). The handoff's `qa.axe.report_path` will point at it (T23).
- The CLI now runs the gates after the build. On a pass it still exits 1, since the link check, fact diff and handoff come in T22 and T23. On a failure it exits 3 but does not yet write the `status: "fail"` handoff; T23 writes the handoff on every path.
- Link check (T22, `qa/links.mjs`): every `href` and `src` on `a`, `link`, `img`, `script`, `source` and `iframe` in the built pages. Internal ones must be a file in `dist/` (a missing one fails the gate). External ones get a HEAD (one GET if HEAD is refused) with a 10 s timeout; a dead one goes in `broken[]` but never fails the gate. mailto, tel, data and `#` anchors are skipped, and so are preconnect hints (they are not links). `checked` counts unique link and page pairs; `from` is the page slug.
- Fact diff (T22, `qa/factdiff.mjs`): each inventory fact is judged first inside the element rendered from its own block (`data-src`), so a copy of the phone number elsewhere on the site cannot hide a changed digit on the contact page. Phones compare by digits, emails case-insensitively, everything else by its words (inside its own block the words may be in any order, so "Principal: Dana Whitfield" holds "Dana Whitfield, Principal"; elsewhere they must appear as a phrase). If the fact is not in its block, an exact copy anywhere on the site counts (a legal notice's name is usually its section heading). A phone or email one or two characters off is `changed` (before and after); anything else not found is `missing`. Facts whose block is in `storyboard.dropped` are skipped and not counted in `checked`. Any changed or missing fact fails the gate, naming the fact id and the page.
- Changed versus missing (T22): only phones and emails are detected as `changed`. A wrong digit in a date, time, address or price shows up as `missing`. It still fails the gate; only the label differs.
- Regex limits (T22): the phone and email patterns have bounded repeats. Unbounded, the email pattern took 50 s on a 200,000-character block; bounded, the worst case is about 150 ms. A test fails if a huge block takes over 3 s.
- The CLI runs all three gates (accessibility, links, facts) before deciding, so one failed run lists everything to fix, then exits 3.
- Handoff (T23): written on a pass (exit 0, `status: "pass"`) and on a gate failure (exit 3, `status: "fail"`, with the failures in the report), always validated against handoff.v1 before writing. The stage prints one line to stdout on a pass. All paths are relative to the run folder with forward slashes: `c-build/site` (repo), `c-build/site/dist` (preview), `c-build/site/dist/<page>.html`, `c-build/screens/<slug>-desktop.png` and `-mobile.png`, `c-build/axe.json`, `c-build/report.md`. `preview_url` stays null until a host is approved (T30). `cost_usd` is 0.
- Screenshots (T23, `handoff/screens.mjs`): full page, at 1280 px and 390 px wide, with reduced motion and fonts loaded, taken from the same local server as the QA tools. The blind test kit reads them.
- Fidelity (T23, `handoff/fidelity.mjs`): `pages_total` is the pages crawled plus the pages that failed to load; `pages_carried` is the crawled pages some new page is built from. **Dropped** lists, without repeats: the storyboard's own drops, pages that failed to load, crawled pages no new page uses, forms that need no backend (not rebuilt), section images with no saved file, and every link to another website on the old site. **Flagged** lists forms that needed the old server and now show the call or email note; such a form is flagged instead of dropped even when the storyboard dropped it, because Lane C did carry a replacement. Dashes in reasons are replaced like everywhere else.
- Report (T23, `handoff/report.mjs`): written for a school office. Its third line says "Ready to publish" or "Not ready to publish" with the number of problems; then the carried and left-out counts, the problems to fix (on a fail), the pages, every dropped and flagged item with its reason, and the four checks in plain words.
- Site repo (T23, `handoff/repo.mjs`): `git init` on `main`, a README (see it, put it online, the page list, how to change and rebuild), a `.gitignore` for `node_modules/` and `.astro/`, and one commit by "Redesign Agent" set with `git -c`, so it never depends on the machine's git identity. `dist/` is committed so a non-technical owner can upload it as is. The README says `npm install`, not `npm ci`, because the site has no lockfile.
- Integration ready means: on the sample, `build` exits 0 and writes a handoff that passes our own handoff.v1 check, every path in it exists, and every page slug is a storyboard page. These are the checks `contracts/validate.mjs --cross` makes for a handoff. Lane C does not run that script (lane `CLAUDE.md`); the orchestrator runs it on integration.
